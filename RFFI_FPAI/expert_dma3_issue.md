# 专家特征模块（expert_feat_rffi）上板实测问题（第 3 版）

日期：2026-10-26　　平台：ZG330 / 30TAI，PL 200 MHz，PS 侧 `impl_fpai_app`（aarch64）

## 结论先行

1. **上一版的 CFO 问题已修好。** 新 bit 上 f31 稳态槽 193 维与黄金模型逐字一致
   （CFO 9/9；FFT log 幅度有 ≤10 LSB 的既有小差、1 个累积量角度差 1 LSB，其余全 0）。
2. **第 2 版里“读 feature 缓冲跑在写前面 / header 新 payload 旧”的判断是错的，撤回。**
   输出乒乓握手本身正确（`feat_valid` 门控，见第 3 节）。
3. **真正的问题在输入侧：PL 输入环里多进了帧，处理流整体滞后约 3 帧。**
   表现为每次调用前 3 槽（0/1/2）的 193 维是用**上一次调用的输入**算出来的，
   槽 3..7 才是本轮输入。多出来的输入帧来自 MM2S 单描述符自环的重发（PS 侧）。
4. **每轮打包的帧数正好是 8，没有“多算的帧”。** 这一点由 `out_idx` 的
   ctr 序列证明（见 4.2），不能用“多打包了第 9/10/11 帧”解释。

---

## 1. 复现条件

- PS 程序：`impl_fpai_app/build/rffi_deploy`，配置 `configs/diag_expert_shift0.yaml`。
- 输入：file 模式 32 帧；`tta_shifts: [0]` ⇒ **每次 HLS 调用喂 8 个逐位相同的
  shift-0 帧**（8 × 1024 B，MM2S 一次写完；`.in` dump 已验证 8 槽逐字节相同）。
- 输出：dma3 S2MM 按帧收 8 × 1024 B。

## 2. 现象

`diag6.log`（32 帧）：`f00~f03` 干净，`f04` 起**连续 28 次调用**出现，形态固定为

```
f08  XXX.....   槽 0/1/2 = 上一次调用的结果，槽 3..7 正确
f09  XXX.....
...
f31  XXX.....
```

偶发变体：f04 `....XX..`、f07 `XXXX....`、f11/f15/f26/f29 `XXX....X`、
f19 `...XXXXX`（槽 3..7 五个互不相同）。这些是输入环滞后量在变化时的过渡形态。

## 3. 已验证：输出握手是对的

- `pk_idx == 255` 那一拍才置 `feat_valid[wr_bank]`（expert_feat_rffi.v L705-708）；
- AXIS 引擎只在 `feat_valid[ob]` 时起帧（L788）；
- 第 255 字握手完成才释放 bank（L587-588）；
- 读地址流水在 `out_cnt=k` 时给第 k 字，没有“读比写快”的通路。

⇒ 每条输出帧都是完整打包过的，不存在“半写 bank 被读出去”。

## 4. 定案：输入侧滞后 3 帧

### 4.1 前 3 槽就是用上一次调用的输入算的（黄金模型逐字核对）

- f31 槽 0/1/2 的 193 字，与 f30 稳态槽**逐位相等**（差 0 字）。
- 拿 `f31`/`f30` 的 `.in` 各自过黄金模型：
  - f30 稳态槽 vs `golden(f30.in)`：差 40 字；
  - **f31 槽 0 vs `golden(f30.in)`：也差 40 字**；
  - f31 稳态槽 vs `golden(f31.in)`：差 111 字（FFT 区域差异随输入不同）。
- 也就是说，那 3 槽不是“旧 bank 残留”，而是**用 f30 的 8 帧原样数据重新算了一遍**。

### 4.2 没有“多算 3 帧被打包”——ctr 序列排除这个解释

- `out_idx` 是 3 bit 自由计数，只在模块复位时清零（L521），每打包一帧 +1（L711），
  header 第 195 字 = `out_idx`（L770）。**不是每轮清零。**
- 如果每轮多打包 3 帧，读窗口起点的 ctr 会每轮前进 3（0、3、6、1……）。
- 实测 `diag6.log` 28 个窗口**全部是严格的 `0,1,2,3,4,5,6,7`**。
- ⇒ 每轮打包帧数正好 8，多出来的输入帧没有变成额外输出，而是留在输入环里，
  让处理流整体滞后（本轮前 3 帧消费的是上一轮输入的残留）。

### 4.3 多出来的输入帧来自 MM2S 单描述符自环

- `pl_dma_io.c` L793-794：MM2S 单描述符，`NXTDESC` 指向自己，注释已写明
  “传完必须马上复位，否则硬件会把同一个描述符再跑一遍”。
- `pl_dma_io.c` L1027：`mm2s_stop()` 要等 `xfer_direct()` 收满 8 帧 dout 之后才调，
  中间隔着 1~3 个 HLS 帧，重发的正是本轮 SRC 里的同一批数据。
- 板端日志有 `DMASR=0x0001100a [IOC]` 与 `DMAIntErr(描述符 buffer length=0)`，
  与“描述符完成后被再取一次”一致。
- 这也解释了 4.1：重发的输入与上一轮逐位相同，所以算出来的特征也逐位相同。

## 5. 修法（PS 侧，PL 侧无法区分重发帧）

1. **别靠事后复位**：收 dout 的等待循环里每圈读 `MM2S_SR`，一见 `IOC` 立刻
   `chan_reset(MM2S)`。能掐掉大部分重发，但仍是竞态，会漏几帧。
   更彻底的是让自环能真正终止（`NXTDESC` 指向能停的地方），而不是靠复位。
2. **改完必须验证滞后是否真的消失**：PL 输入环里已经积着的 3 帧不会自己排空
   （每轮 8 进 8 出、速率相同，会一直吊着）。若改完仍是 3 槽不一致，
   需要在开库时把 PL 复位一次或加一次排空。

## 6. 验收判据

喂 64 次调用，每次 8 帧相同、相邻两次不同：

- 每次调用内 8 帧 193 维必须逐位相同（现在 28/32 次挂）；
- 每帧必须等于黄金模型该帧结果（现在只有槽 3..7 过）；
- 64 次里允许 0 次不一致。
